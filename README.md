# testkit-k6

Builds Testkit's custom k6 executable and publishes it to npm as platform
packages. Testkit installs them as exact optional dependencies and runs the
binary directly; nothing here runs during a Testkit build or release.

## What the executable is

Stock k6 cannot talk to a database. Testkit's k6 runs are seeded and asserted
against Postgres, so the executable bundles two extensions:

- `go.k6.io/k6` 1.7.1 (AGPL-3.0)
- `github.com/grafana/xk6-sql` 1.0.6 (Apache-2.0)
- `github.com/grafana/xk6-sql-driver-postgres` 0.1.2 (AGPL-3.0)

It is assembled by `go.k6.io/xk6` 1.4.2 and compiled with Go 1.25.10, cgo
disabled, vendored modules, `-trimpath`, `-buildvcs=false`, and
`-ldflags=-s -w -buildid=`. The same inputs produce byte-identical
executables on any host.

## Packages

| Package                                     | Contents                                                  |
| ------------------------------------------- | --------------------------------------------------------- |
| `@gfdelarue/testkit-engine-k6-darwin-arm64` | `bin/k6`, `metadata/`, `licenses/`, `SOURCE.md`           |
| `@gfdelarue/testkit-engine-k6-darwin-x64`   | same                                                      |
| `@gfdelarue/testkit-engine-k6-linux-arm64`  | same                                                      |
| `@gfdelarue/testkit-engine-k6-linux-x64`    | same                                                      |
| `@gfdelarue/testkit-engine-k6-win32-x64`    | `bin/k6.exe`, `metadata/`, `licenses/`, `SOURCE.md`       |
| `@gfdelarue/testkit-engine-k6-source`       | vendored source archive, `source-manifest.json`, licences |

Each platform package carries `os` and `cpu` fields, so npm installs only the
one matching the host, and depends on the source package at the same exact
version. `metadata/provenance.json` records the builder inputs and the
executable digest; `metadata/sbom.spdx.json` lists the linked Go modules.

All six packages share one version line that is independent of both k6 and
Testkit. A rebuild of the same inputs bumps the patch number; a k6 or extension
upgrade bumps the minor number. The k6 version is recorded in each manifest's
`testkit.k6Version` field and in the package description.

## How Testkit consumes them

Testkit's root `package.json` pins the five platform packages at one exact
version under `optionalDependencies`. `npm ci` fetches the host's package with
npm's own integrity check, and Testkit resolves the executable from its root
package through the `./binary` export. There is no download step, no PATH
lookup, and no fallback to a system k6. A consumer that installs with
`--omit=optional` gets a clear error from Testkit.

## Cutting a release

1. Edit `src/contract.ts`: bump `K6_RELEASE.packageVersion`, and for a k6 or
   extension upgrade also update `K6_BUILD_CONTRACT` (versions, commits, xk6
   checksums) and `sourceArchive`/`sourceRoot`.
2. Regenerate locally and accept the new source identity:

   ```sh
   npm run build -- --refresh-source --all --accept-source
   ```

   This rewrites `source-manifest.json` and prints the five executable digests.
   Copy them into `K6_RELEASE.expectedExecutables`, then run the same command
   without `--accept-source` to confirm the build is stable.

3. Open a pull request. The Verify workflow regenerates the source on the
   self-hosted orthrus runner (labels `testkit-k6`, `orthrus-ubuntu`),
   rebuilds all five targets, and fails unless every executable matches
   `expectedExecutables` and the regenerated `source-manifest.json` matches
   the committed one. The Release workflow runs on the same runner.
4. Merge, then tag:

   ```sh
   git tag v1.2.3 && git push origin v1.2.3
   ```

   The Release workflow rebuilds from scratch, refuses to run if the tag does
   not equal `v<packageVersion>` or any package version already exists, then
   publishes the source package followed by the five platform packages with
   npm trusted publishing. Provenance attestations are generated by npm.

5. In Testkit, update the five `optionalDependencies` pins and, for a k6
   upgrade, the expected k6 version constant in the resolver.

## Reproducibility

`source-manifest.json` is the pin for the generated source tree: archive
SHA-256 and size, the complete module graph with Go checksums, licence file
digests, and the exact generator command. The archive itself is not committed;
every build regenerates it from the pinned module versions and fails if the
result differs. `K6_RELEASE.expectedExecutables` pins the five output digests.

Build outputs live under `.state/` and are ignored by git.
